# Contributing To Sparki Documentation

Sparki documentation should be calm, precise, and durable. Write for the engineer, designer, support lead, or founder who will need this context six months from now.

## Purpose

Create a shared operating system for product decisions, technical direction, research, and team memory.

## Constitutional Authority

The [Product Constitution](blueprint/00-product-constitution.md) is the highest authority in the repository.

Before proposing, reviewing, or accepting a product decision, verify that it aligns with the Constitution. If a contribution conflicts with the Constitution, either revise the contribution or propose a formal constitutional amendment.

## Contribution Standards

- Prefer short documents with clear sections.
- Avoid speculative detail unless it is labeled as a hypothesis.
- Link related documents instead of repeating large blocks of context.
- Record decisions in ADRs when they affect architecture, product philosophy, or long-term constraints.
- Reference the Constitution for product principles instead of duplicating them.
- Keep clinical workflow language understandable to non-clinicians.
- Prefer plain language over corporate, academic, or unnecessarily technical terms.
- Update open questions when a decision is made.

## Document Lifecycle

- `Draft` - Initial thinking; incomplete and expected to change.
- `Active` - Used by the team for current decisions.
- `Accepted` - Decision or direction is approved.
- `Superseded` - Replaced by a newer document or ADR.
- `Archived` - Preserved for historical context only.

## Review Expectations

Documentation changes should be reviewed for:

- Accuracy
- Clarity
- Consistency with the Product Constitution
- Plain language
- Useful links to related docs
- Separation of facts, decisions, and open questions

## Notes

Good documentation should make the company faster without making the company heavier.
